# API для работы с external_code (универсальными внешними кодами)

## Описание

`external_code` — стабильный строковый идентификатор (обычно UUID), по которому внешние системы находят станцию или агрегат **в любой версии базы данных**. Внутренний числовой `id` при копировании версии меняется, а `external_code` у копии той же логической сущности сохраняется.

Документ отражает поведение моделей `Station` и `Machine` в приложении (слушатели SQLAlchemy `before_insert`) и типовые сценарии: **копирование версии БД** и **импорт из Excel**.

---

## Как формируется `external_code` (текущая реализация)

### Общее

- Значение задаётся только при **вставке** строки (`before_insert`). При **обновлении** (`UPDATE`) код **не пересчитывается** — смена названия, мощностей, справочников и т.п. не меняет `external_code`.
- Если при создании объекта в ORM поле `external_code` уже заполнено, генератор **не трогает** его.

### Станция (`Station`)

Файл: `app/generation/models/station/station_model.py`.

1. Уже задан `external_code` — выход.
2. Иначе в таблице станций ищется запись с тем же нормализованным `name` и тем же ключом субъекта РФ (`RegionalDistrict`: номер, имена, `ref_uuid`). При **однозначном** совпадении подставляется **существующий** `external_code` (в т.ч. из другой версии БД в той же таблице).
3. Иначе генерируется **`uuid5(uuid.NAMESPACE_URL, _station_key(...))`**, где `_station_key` собирается из `name` / `name_combined` / `name_so` и ключа района (приоритет полей задан в коде).

Итог: для новой электростанции код либо **наследуется** по имени и субъекту, либо **детерминированно** выводится из ключа; случайный UUID **не** используется в самом слушателе.

### Агрегат (`Machine`)

Файл: `app/generation/models/machine/machine_model.py`.

1. Уже задан `external_code` — выход.
2. Иначе, если у агрегата есть **`id_ti`** и по всем строкам `gs_gen_machines` с этим `id_ti` в БД получается **один** ненулевой `external_code`, он **наследуется**.
3. Иначе ищется строка с тем же **`external_code` электростанции** (по `id_station`), **`machine_number`**, **`machine_name`** (после схлопывания пробелов в Python) и **`date_exploitation`** (оба `NULL` или даты равны). При однозначном совпадении код **наследуется**.

   Важно: сопоставление по имени/номеру в SQL **жёсткое** (trim и равенство строк). Вспомогательные нормализации вроде «скобки в конце имени» в логике наследования кода **не участвуют**.

4. Если подходящей записи нет — выдаётся **новый `uuid4()`** как постоянный идентификатор логического агрегата; он **не** является формулой от полей и дальше **не пересчитывается**.

Итог: код агрегата — это либо наследование по `id_ti`/сигнатуре при вставке, либо **случайный UUID**, закреплённый за строкой.

## API Endpoints

### 1. Получить станцию по external_code

**GET** `/generation/stations/api/external_codes/station/<external_code>`

**Пример запроса:**
```bash
curl http://msk-arm-gs01.ntcees.ru/generation/stations/api/external_codes/station/5aa8d4b9-1348-588a-8974-d3d590e629d7
```

**Пример ответа:**
```json
{
  "type": "Электростанция",
  "external_code": "abc-123-def-456",
  "database_version_id": 7,
  "database_version": "Наименование версии базы данных",
  "id_station": 123,
  "name_station": "Название электростанции",
  "regional_district": "Наименование субъекта",
  "station_type": "Наименование типа электростанции",
  "gen_company": "Наименование генерирующей компании"
}
```

### 2. Получить агрегат по external_code

**GET** `/generation/stations/api/external_codes/machine/<external_code>`

В ответе возвращаются актуальные поля агрегата и электростанции (в т.ч. `station_external_code`). Сам `external_code` агрегата **не** вычисляется из этих полей при чтении — это сохранённое значение из БД.

**Пример запроса:**
```bash
curl http://msk-arm-gs01.ntcees.ru/generation/stations/api/external_codes/machine/e7a8ed52-10ed-51fc-a521-fcf9649ef2d8
```

**Пример ответа:**
```json
{
  "type": "Агрегат",
  "external_code": "e7a8ed52-10ed-51fc-a521-fcf9649ef2d8",
  "database_version_id": 7,
  "database_version": "Наименование версии базы данных",
  "id_machine": 789,
  "machine_number": "1",
  "machine_name": "Название агрегата",
  "id_station": 123,
  "station_external_code": "abc-123-def-456",
  "equipment_group": "Наименование группы оборудования",
  "regional_district": "Наименование субъекта",
  "gen_company": "Наименование генерирующей компании"
}
```

### 3. Batch запрос

**POST** `/generation/stations/api/external_codes/batch`

Тело: JSON со списками кодов станций и агрегатов (см. реализацию в `app/generation/routes/stations/api_external_codes_routes.py`).

## Сценарий: копирование версий базы данных

Копирование выполняется сервисом версий (например `_copy_version_data_staged` / `_copy_table_with_mapping` в `app/common/services/database_version_services.py`).

Что происходит с `Station` и `Machine`:

1. Строки **читаются** из источника по `database_version_id` и **вставляются** в ту же таблицу с новым `database_version_id` и **новым** суррогатным `id`.
2. В INSERT попадают **все колонки**, кроме `id` и `database_version_id`, в том числе **`external_code`**, как в исходной строке.
3. Вставка идёт **на уровне SQL**, без прохода через ORM-слушатели `before_insert` у моделей. То есть при копировании версии **не** вызывается логика «uuid5 / поиск по имени / uuid4».

**Следствие:** после копирования версии станция и агрегат в новой версии сохраняют **те же** `external_code`, что и в источнике. Это основной способ гарантировать одинаковые коды у «одной и той же» сущности в разных версиях, если исходная версия уже была заведена корректно.

Если же агрегат в одной версии создан с «лишним» уникальным `uuid4()`, копия унаследует именно его; автоматического слияния с другой версией при копировании нет. Для выравнивания семейств агрегатов между версиями в репозитории есть вспомогательный скрипт `scripts/sync_machine_external_codes.py` (и сопутствующие утилиты для коллизий станций).

## Сценарий: загрузка данных из Excel (генерация / электростанции)

Импорт станций и агрегатов из Excel: `app/generation/services/station_services/import_station_services.py`.

### Станция

- При **создании новой** электростанции в коде импорта задаётся:
  - `external_code=str(uuid4())`, если в текущей (версионируемой) выборке уже есть кандидаты с тем же именем и субъектом (`station_candidates` непустой);
  - иначе `external_code=None`.

- Если передано `None`, срабатывает ORM `before_insert` у `Station`: возможны **поиск существующего кода** по имени и субъекту или **`uuid5`** от ключа.
- Если передан **явный `uuid4()`**, слушатель **не** перезаписывает код — новая станция получает **новый случайный** UUID, даже при совпадении имени с другими версиями. Так отделяют вторую (и далее) запись электростанции с тем же именем и районом в одной версии от «первой».

**Практический вывод:** при чистом импорте «первая» станция с данным именем в субъекте чаще попадает в ветку `external_code=None` и может **склеиться** по коду с уже существующими строками в БД (другая версия). Дополнительная станция-«слот» с теми же атрибутами получает **отдельный** случайный код.

### Агрегат

- В конструкторе `Machine(...)` при импорте **`external_code` не передаётся**.
- При первом сохранении срабатывает `before_insert` у `Machine`: наследование по `id_ti` или сигнатуре (станция + номер + имя + дата ввода), иначе **новый `uuid4()`**.

**Практический вывод:** если агрегат впервые создаётся только в новой версии и в БД нет строки с тем же `id_ti` или точно совпадающей сигнатурой, он получит **новый** случайный код — он **не** совпадёт с другой версией до ручного выравнивания или до совпадения сигнатуры при создании. Копирование версии с уже правильными кодами надёжнее, чем независимый импорт тех же строк в каждую версию.

---

## Поведение при изменении полей (не импорт и не копирование)

Изменение «бизнес-полей» (название, мощность, даты, справочники) через UI или API обновления **не меняет** `external_code`. Внешние интеграции могут продолжать запросы по старому коду.

Риски расхождения кодов между версиями возникают, когда **новые** строки создают отдельно в каждой версии (импорт, ручное создание) и сигнатура/ `id_ti` не совпадают с уже существующими записями.

## Как это работает на практике для интеграций

### Экспорт и хранение кодов у внешней системы

1. Внешняя система получает выгрузку (Excel/CSV/API), где есть `external_code` для станций и агрегатов.
2. Сохраняет коды у себя как ключи.
3. По ним запрашивает актуальные данные через GET/batch (см. выше).

### Массовая синхронизация

1. Собрать списки `external_code` для станций и машин.
2. Вызвать batch endpoint одним запросом.
3. Обновить локальные записи по ответу.

---

## Преимущества использования external_code

1. **Стабильность при копировании версии** — коды переносятся вместе со строками.
2. **Стабильность при правках** — код не пересчитывается при UPDATE.
3. **Независимость от `id`** — после копирования версии числовые идентификаторы новые, внешний ключ остаётся прежним.

Ограничение: **уникальность «один агрегат — один код во всех версиях»** для данных, созданных раздельно импортом, обеспечивается не формулой, а совпадением сигнатуры/`id_ti` при вставке или последующими скриптами синхронизации.

## Обработка ошибок

Если запрашиваемый `external_code` не найден в текущей конфигурации запроса, API возвращает **404** (см. обработку в маршрутах).

## JSON-обмен: версии БД и наборы datasets

Два независимых API под префиксом `/api`.

### 1. Сведения о версиях БД (отдельный API)

Сначала клиент получает список версий и выбирает id.

**GET** `/api/database_versions`

```json
{
  "rows": [
    {
      "database_version": 7,
      "version_number": "ГС-2026",
      "description": "",
      "planning_scheme": "gs",
      "current_year": 2024,
      "period_start": 2026,
      "period_end": 2042
    }
  ]
}
```

**GET** `/api/database_versions/<id>` — одна версия; неизвестный id → **404**.

`database_version` — id (`gs_sys.gs_database_versions.id`); его передают в запрос наборов.

`planning_scheme` — `"sipr"` | `"gs"` | `null` (по номеру версии, как на `/refdata/`).
`current_year` / `period_start` / `period_end` — те же величины, что в наборе `general_info`
для этой версии. **СиПР и Генеральная схема — разные версии БД**, не два разных API наборов:
клиент выбирает нужный id в списке версий, затем запрашивает `/api/datasets/<id>`.

### 2. Один API для JSON-наборов

После выбора версии — запрос **только по id** (без имени набора в URL).

Как открывать:

| URL | Поведение |
|-----|-----------|
| `GET /api/datasets` | JSON **в браузере** — список имён наборов |
| `GET /api/datasets/<id>?year=2030` | JSON **в браузере** — выгрузка с фильтром лет |
| `GET /api/datasets/<id>` | **файл на скачивание** — полная выгрузка (тяжёлый ответ) |

Примеры:

- http://127.0.0.1:5000/api/datasets — JSON в браузере  
- http://127.0.0.1:5000/api/datasets/46?year=2030 — тоже в браузере  
- http://127.0.0.1:5000/api/datasets/46 — полная выгрузка, файл на скачивание  

Сейчас в выгрузке: `general_info`, `gentypes_info`, `generation_objects`, `generation_machines`.
Набор `equipment_group_params` временно скрыт (код сборки сохранён).

**GET** `/api/datasets/<database_version>` — все наборы этой версии БД.

Ответ:

```json
{
  "database_version": 7,
  "version": 7,
  "datasets": [
    {
      "dataset": "general_info",
      "database_version": 7,
      "version_number": "ГС-2026",
      "version": 7,
      "comment": "",
      "rows": [
        {
          "Текущий год": 2024,
          "Начало периода": 2026,
          "Конец периода": 2042
        }
      ]
    },
    {
      "dataset": "gentypes_info",
      "database_version": 7,
      "version_number": "ГС-2026",
      "version": 7,
      "comment": "",
      "rows": []
    },
    {
      "dataset": "generation_objects",
      "database_version": 7,
      "version_number": "ГС-2026",
      "version": 7,
      "comment": "",
      "rows": []
    },
    {
      "dataset": "generation_machines",
      "database_version": 7,
      "version_number": "ГС-2026",
      "version": 7,
      "comment": "",
      "rows": []
    }
  ]
}
```

- В URL только числовой id версии; имя набора (`generation_objects` и т.п.) — внутри элементов `datasets`.
- Query (опционально): `year`, `start_year`, `end_year` — при наличии фильтра ответ открывается в браузере; без фильтра — скачивание файла.

Годы по умолчанию (полная выгрузка временных рядов): пять последних фактических, текущий (оценка) и все плановые годы этой версии (набор `general_info` от фильтра лет не зависит).

Legacy-алиасы: `/generation/stations/api/datasets/<database_version>`.

### Период версии — `general_info`

Одна строка из блока «Периоды планирования» на `/refdata/`:

| Поле | Источник |
|------|----------|
| Текущий год | признак года «текущий (оценка)» |
| Начало периода | начало СиПР / ГС на `/refdata/` (`year_sipr_start`) |
| Конец периода | для версии «СиПР» — `year_sipr_end`; для «ГС» — конец Генеральной схемы (2042) |

### Зона × год — `gentypes_info`

Строка — как в mock коллег (ключи с «млрд»/«МВт» в имени сохранены).
Потребление: значение из БД (млн кВт·ч) делим на 1000 (млрд) для всех зон, включая ЕЭС.
Источники:

| Поля | Страница АРМ |
|------|----------------|
| Максимальная мощность (=уст. мощность), максимум потребления, экспорт мощности, ограничения, вводы после максимума, перетоки | `/energy_balance/power_balance/` |
| Потребление, ГАЭС (charge), экспорт ЭЭ | `/energy_balance/ee_balance/` (+ `gs_gen_station_gaes_charge_consumptions`) |
| ЧЧИУМ, дата/время максимума | `/power_demand/summary/oes/` |
| ТНВ, combined_on_ees | параметры нагрузки (`gs_pd_*_demand_params`; на сводке PD) |

Капвложения всегда `0`. Полей ОЗП в mock нет — в выгрузку не входят.

Зоны: ЕЭС + все СЗ + все ОЭС версии (без «не указано» и «Новые территории»).
Годы: от текущего − 5 до конца расчётного периода СиПР/ГС (`/refdata/`).

### Станция × год — `generation_objects`

Строка: `external_code`, название, тип станции, год, субъект, зона, номер энергозоны,
сумма Руст неархивных агрегатов (МВт), годовая выработка (значение как в БД, млн кВт·ч;
ключ в JSON — «Производство электроэнергии в году, МВт*ч», 3 знака после запятой),
признак «планируемая»
(`true`, если у всех неархивных агрегатов ожидаемый год ввода ≥ текущего года версии
и фактическая дата ввода в работу пуста).

### Агрегат × год — `generation_machines`

Строка: `station_external_code` (тот же код, что у станции), `external_code` агрегата,
год, номер и название агрегата, тип блока, Руст агрегата, тип топлива,
тип группы оборудования (`gs_sys_equipment_groups`), топливная группа оборудования
(имя и `equipment_group_external_code` из `gs_fue_equipment_groups`),
год ввода, год вывода, признак архивности.

### Группа оборудования × год — `equipment_group_params` (временно скрыт)

Сейчас не входит в `GET /api/datasets` и `GET /api/datasets/<id>`.
Сборка: `app/api/services/equipment_group_exchange_services.py`.

Строка: `external_code` группы, `station_external_code`, название, тип группы оборудования,
тип и доступность технологии, код `numb`, год и основные топливные параметры
(`nust`, `nr`, `h`, выработка/отпуск ЭЭ и ТЭ, СН, расход топлива, тепловая мощность).
Связь с агрегатом — `equipment_group_external_code` в `generation_machines`.
