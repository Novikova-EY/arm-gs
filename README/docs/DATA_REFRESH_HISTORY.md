# История причин обновления данных

Первый этап для Спроса, Нагрузок и Энергобалансов. Общая панель сохраняет прежнюю кнопку и проверку несохраненных правок. В строке с заголовком отображается время формирования страницы в компактной светлой плашке; на узких экранах плашка переносится под заголовок. После обнаружения новой версии появляется ссылка «Что изменилось?». При наличии событий ссылка доступна и без красного предупреждения: например, после собственного автосохранения.

## Интерфейс

Диалог показывает изменения после загрузки текущей страницы:

- время операции в часовом поясе браузера;
- вид операции: добавление, изменение, удаление, сохраненная часть импорта, пересчет с сохранением, формулы или примечания;
- модуль и категорию данных;
- названия объектов;
- инициатора;
- для каждой записи: объект, период и измененные поля в формате «было → стало».

ID записей не показываются, в том числе в ранее сохраненных событиях. Период указывается рядом с объектом изменения; отдельная строка «Годы» выводится только для событий без подробностей.

Подзаголовок с общими пояснениями, счетчик операций с записями и нижний блок о влиянии на таблицу не выводятся. Названия полей и формат значений используют существующие средства журнала. Названия связанных объектов читаются в той же версии БД и кешируются на время транзакции. Если старое событие было записано без подробностей, интерфейс сообщает об этом, не восстанавливая значения предположительно.

Список открывается без обновления таблицы и без подтверждения изменений. Кнопка обновления в диалоге использует тот же обработчик, что и основная кнопка. Отмена подтверждения сохраняет введенные значения. При повторной загрузке страницы формируется новая точка отсчета. Старые события в новый список не попадают. Отметка «Данные страницы на» показывает время загрузки, а не текущее время: она меняется после успешного обновления с перезагрузкой страницы, но не при фоновом опросе, отмене подтверждения или ошибке обновления.

Список выдается по 20 операций, с кнопкой «Показать еще». Несколько сохранений в одном HTTP-запросе объединяются в одну операцию. Для фонового импорта с перенесенным контекстом запроса действует то же объединение. Вне запроса границей операции служит внешняя транзакция. Записи импорта означают именно сохраненные изменения, а не гарантированное завершение всего задания: отдельный итог задания здесь не отображается.

## Источники

Используются существующие зависимости счетчиков трех модулей, а не второй независимый список правил инвалидации:

| Модуль | Источники |
| --- | --- |
| Спрос | Спрос, генерация, справочники, территории |
| Нагрузки | Нагрузки, Спрос, долгосрочный прогноз потребления, генерация, справочники, территории |
| Энергобалансы | Энергобалансы, генерация, перспективные площадки, Спрос, Нагрузки, топливные данные, справочники, территории |

История и счетчик операций фильтруются строго по отображаемой версии БД. Записи других версий, события без установленной версии и общие источники без привязки к версии не показываются, в том числе администратору. При отсутствии выбранной версии список пуст. Массовые ORM update/delete разделяются по версиям фактически измененных строк; для insert используется явно переданная версия. Версия открытой страницы не подставляется в неизвестный источник. При переносе записи между версиями старая версия видит удаление старых значений, новая – добавление новых, без раскрытия содержимого другой версии.

Названия объектов и подробности из другого модуля скрыты для обычного пользователя. Инициатор чужой операции отображается как «Другой пользователь»; собственное имя, системный процесс и имена в режиме администратора доступны. Подробности содержат старые и новые значения только разрешенных событий выбранной версии БД.

## Хранение и согласованность

Таблицы `gs_data_refresh_state` и `gs_data_refresh_events` в схеме журнала содержат события и подробности в JSON-поле summary. Новая миграция для подробностей не требуется. Они заполняются в той же транзакции, что и исходные данные. Rollback, откат savepoint и неудачный commit не оставляют событий. Снимок до изменения берется из БД, поэтому прежнее значение сохраняется и для истекших ORM-атрибутов. Присваивание прежнего значения и массовый update без фактических изменений не создают событие.

Причины собираются во время flush и записываются непосредственно перед commit внешней транзакции. Единственная строка состояния выдает последовательные ревизии под транзакционной блокировкой. Это не допускает пропуска поздно завершившейся транзакции с ранее выделенным номером. Блокировка журнала берется только после финального flush, а не на все время обработки длительного импорта. Конкурентные записи и большие импорты требуют нагрузочной проверки на целевой PostgreSQL.

Курсор подписан и привязан к модулю, версии БД и поколению журнала. Он снимается до построения таблицы. Redis не хранит историю; его очистка не удаляет причины. Существующий механизм красного предупреждения и подтверждения собственных автосохранений не заменяется новым счетчиком истории.

Автоматической очистки истории нет. Подробности старых событий без сохраненных снимков восстановить нельзя. Точный расчет влияния по фильтрам и подсветка ячеек не входят в этот этап. SQL, выполненный напрямую через соединение или вне ORM, не отслеживается. Для bulk insert сохраняются явно переданные значения; upsert и значения, вычисленные сервером БД при такой вставке, не реконструируются. Изменение первичных ключей через массовые UPDATE не поддерживается журналом подробностей.

## API и ошибки

Для каждого из трех блюпринтов:

- `GET /data-revision/?history_cursor=...` дополнительно возвращает доступность истории и число операций; без параметра прежний формат ответа сохранен;
- `GET /data-changes/?history_cursor=...&before=...` возвращает страницу сгруппированных событий и границу следующей страницы.

Требуется вход в систему. Ответы истории имеют `Cache-Control: no-store, private`. Несовпадение поколения или версии БД выводится отдельно. Ошибка чтения истории не блокирует проверку прежнего счетчика и ручное обновление. Если красная кнопка появилась, но событий текущей версии нет, диалог сообщает об отсутствии изменений в текущей версии, не показывая события других версий. Открытие истории не снимает красное состояние.

## Установка

Перед запуском новой версии приложения применить миграции штатным способом:

```text
flask --app run:app db upgrade
```

Новая ревизия: `gs26110301`, родитель: `gs26110202`. Миграция добавляет две таблицы и индексы, не меняя исходные данные. Затем перезапустить процессы приложения и заново открыть страницы. До применения миграции запуск рабочих сохранений с новым кодом недопустим: журнал является частью транзакции сохранения.

- Существующие проверки обновления Спроса, Нагрузок и Энергобалансов сохраняют прежний контракт.
