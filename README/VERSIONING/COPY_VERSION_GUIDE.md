# 🔄 Копирование данных между версиями

## Проблема

Когда вы создаете новую версию, она **пустая** - в ней нет данных. Это потому что записи привязаны к другим версиям через поле `database_version_id`.

## Решения

### Способ 1: Скрипт копирования данных (Рекомендуется)

**Использование:**

```bash
python copy_version_data.py
```

**Что делает скрипт:**

1. Показывает все доступные версии
2. Показывает статистику по данным в каждой версии
3. Позволяет выбрать **исходную** версию (откуда копировать)
4. Позволяет выбрать **целевую** версию (куда копировать)
5. Копирует все данные с установкой нового `database_version_id`

**Пример работы:**

```

--------------------------------------------------------------------

  [5] Версия 5: Версия 5

--------------------------------------------------------------------
  stations                  - Всего:  1211
```

**Важно:**
- Данные **дублируются**, исходная версия остается без изменений
- Скрипт копирует все таблицы: stations, machines, fuels, и т.д.
- После копирования активируйте нужную версию

### Способ 2: Использование снимков

**Сценарий:**
1. Создайте снимок текущей версии
2. Создайте новую версию
3. Активируйте новую версию
4. Загрузите снимок (он заменит все данные)

**Проблема:** Загрузка снимка заменяет **ВСЕ** данные в БД, включая другие версии!

**Не рекомендуется** для копирования между версиями.

### Способ 3: SQL вручную

**Для продвинутых пользователей:**

```sql
-- Копирование станций из версии NULL в версию 6
INSERT INTO generation.stations (
    name, 
    id_station_type, 
    id_regional_district,
    -- ... остальные поля ...
    database_version_id
)
SELECT 
    name,
    id_station_type,
    id_regional_district,
    -- ... остальные поля ...
    6 as database_version_id
FROM generation.stations
WHERE database_version_id IS NULL;

-- Аналогично для других таблиц
```

**Проблема:** Нужно знать все поля и связи между таблицами.

```bash
# 6. Переключайтесь между версиями 6 и 7 для сравнения
```

```bash

# 5. Теперь все старые данные доступны в версии 1
# 6. Опционально: удалите старые данные (NULL) после проверки
```

### Сценарий 3: Копировать все данные в новую версию

```bash

# 2. Запустите скрипт

#    Исходная версия: ALL
```

## Удаление данных версии

Если скопировали по ошибке:

```sql
-- Удалить все данные версии 7
DELETE FROM generation.stations WHERE database_version_id = 7;
DELETE FROM generation.machines WHERE database_version_id = 7;
-- и т.д. для других таблиц
```

Или используйте веб-интерфейс для удаления версии (это обнулит database_version_id, но не удалит записи).

## FAQ

### Q: Могу ли я копировать только часть данных?

A: Да, модифицируйте скрипт, добавив дополнительные фильтры в `WHERE` условие.

Например, копировать только станции определенного типа:

```python
where_source = f"database_version_id = {source_version_id} AND id_station_type = 1"
```

### Q: Что будет с ID записей?

A: Создаются новые записи с новыми ID. Исходные записи остаются без изменений.

### Q: Копируются ли связи между таблицами?

A: Нет! Скрипт копирует записи "как есть", с теми же внешними ключами. Это может привести к проблемам, если связанные данные не скопированы.

**Рекомендация:** Всегда копируйте все таблицы вместе.

### Q: Можно ли откатить копирование?

A: Да, если вы не закрыли подключение к БД. В скрипте используется транзакция.

Если уже закрыли - нужно удалить данные вручную:

```sql
DELETE FROM generation.stations WHERE database_version_id = [целевая_версия];
-- и т.д.
```

### Q: Будут ли скопированы связанные данные из refdata?

A: **НЕТ!** Скрипт копирует только таблицы из схемы `generation`.

Таблицы refdata (справочники) обычно используются всеми версиями и не привязаны к конкретной версии.

## Ограничения

⚠️ **Важные ограничения:**

1. **Не копируются:**
   - Таблицы из схемы `refdata` (справочники)
   - Файлы и загрузки
   - История изменений (логи)

2. **Нужно вручную проверить:**
   - Связи между таблицами
   - Уникальные ограничения
   - Бизнес-логику приложения

3. **Производительность:**
   - Копирование 1211 станций + связанных данных занимает 1-5 секунд
   - Для больших объемов (>100k записей) может потребоваться несколько минут

## Альтернатива: Работа с NULL версией

**Самый простой подход:**

1. Оставьте старые данные с `database_version_id = NULL`
2. Они будут доступны во **всех** версиях
3. Создавайте новые данные - они автоматически получат текущую версию
4. Со временем данные разделятся по версиям естественным образом

**Преимущества:**
- Не нужно ничего копировать
- Старые данные доступны везде
- Новые данные версионированы

**Недостатки:**
- Нельзя изменить старые данные отдельно для разных версий
- Смешение версионированных и не-версионированных данных
